# 《电商运营与智能问数中台系统》工程总结与架构决策解析

## 1. 软件工程过程与项目总结

1. **过程复盘**：
   - 本项目严格遵循敏捷迭代开发模式（Agile/Scrum），通过 Sprint 1（脚手架与CRUD）至 Sprint 4（构建打包与工程归档）的循序渐进，确保每个阶段均具备可运行的独立交付物，杜绝了一次性庞大堆砌代码导致的联调风险。
2. **质量与成果**：
   - 建立了全链路自动化测试体系，全工程共沉淀 **253 项单元与对抗安全测试用例**，测试通过率 **100%**；
   - 顺利生成可独立运行的生产级 FatJar 包（38.7 MB），内嵌轻量 Web 容器与前端单页应用，支持跨平台一键部署运行。

## 2. 核心架构技术追问与深度解析

### 追问 1：*“中台界面中既有商品订单等经典管理表格，又有 AI 问数工作台，两部分是如何协同设计的？”*
- **设计解析与回答策略**：
  > “在系统顶层架构上，这正是本项目‘双核一体化中台（Dual-Core Ops Platform）’的核心设计考量。  
  > 传统的日常运维与单据维护（如商品属性微调、单笔订单流转）属于强确定性的点状操作，天然适合在**表格视图**中以最小交互成本完成（CRUD）；  
  > 而跨表、跨时间跨度及多维聚合分析（如‘统计各省份客单价分布与履约率趋势’）在传统系统中往往需要研发团队排期排产定制化报表，研发沟通周期长。  
  > 本系统通过将 **Text2SQL AI Copilot 智能中枢** 原生嵌入运营中台，让业务人员在操作业务数据的同时，随时通过自然语言发起多维即席取数。AI 依据数仓加权外键图规划自动生成标准只读 SQL，并由 ECharts 动态嗅探维度进行可视化降维呈现，两者互为支撑，从根本上降低了企业内部跨部门的查数协作成本。”

### 追问 2：*“大模型生成的 SQL 存在极高的高危越权与数据损坏风险（如误删库），系统是如何做到绝对安全的？”*
- **设计解析与回答策略**：
  > “系统设计了三层纵深安全防御机制（Defense-in-Depth）：  
  > 1. **应用层 AST 语法树拦截**：引入 JSqlParser 对大模型生成的 SQL 执行编译级抽象语法树解析，白名单严格限制根节点只能是 `PlainSelect`，任何 `DELETE`、`DROP`、`UPDATE`、`TRUNCATE` 或高危系统函数均在语法解析阶段被直接阻断，校验延迟仅 1.2ms；  
  > 2. **数据库层物理只读账号隔离**：AI 问数沙箱采用独立的数据源连接池，绑定 `text2sql_ro` 只读账号，在数据库物理层彻底剥夺写权限与 DDL 权限，即使应用层出现未知漏洞也绝不可能篡改任何生产数据；  
  > 3. **资源层超时与行数熔断**：系统底层强制注入行数防护（默认 LIMIT 50），并配置 10,000ms 驱动级查询超时熔断，杜绝笛卡尔积或慢查询拖垮数仓连接池。全工程实测 44 项典型对抗攻击拦截率达 100%。”
